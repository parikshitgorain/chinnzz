# ADR 0008: Eleventy build step

- **Status:** approved
- **Date:** 2026-10-17
- **Decision owner:** Parik
- **Supersedes:** the "no build step" part of ADR 0002

## Context

ADR 0002 chose plain HTML with no build step. That worked for a hand-written one-page site. The revised scope adds a content model with many small files, an admin that writes those files, and a need to render the same values into HTML, metadata and structured data without duplicating copy in templates.

Hand-editing every page section and repeating content in several places would create drift and make the admin harder to build. A small static build step solves that without adding a runtime framework.

## Decision

Use **Eleventy 3.x with Nunjucks templates** for the public site:

- Source templates live in `site/`.
- Content comes from `content/`.
- The build writes static HTML to `site/_site`.
- CSS and JavaScript stay hand written. No client framework, no CSS framework and no bundler beyond Eleventy.
- Cloudflare Pages runs `npm run build:site` and publishes `site/_site`.
- `/api/live` remains a Pages Function and is not part of the Eleventy output.

The build is deterministic. Given the same repository, it produces the same site. No content is fetched from the admin at build time in production. The admin writes files into the repo before the build starts.

## Consequences

Easier:

- One source of content for the page, metadata and structured data.
- Content files can be validated before build.
- The admin can write simple files instead of editing HTML.
- Shared layouts and components become possible without a client framework.

Harder:

- Adds Node and an npm dependency to the project.
- Build failures can block a deploy. The publish flow must show the failure clearly.
- The build output directory must be managed in git ignore and Cloudflare settings.

Now true:

- The public site is generated, not hand edited.
- The admin and public site share `content/`.
- ADR 0002 is superseded only on the build-step point. Its static hosting choice still stands.

## Alternatives considered

| Option | Why not chosen |
|---|---|
| Keep plain HTML and inject content with client JavaScript | Slower first paint, worse SEO and a runtime dependency. |
| Astro | Capable, but more framework than a single page needs. |
| Next.js static export | Heavy for one page and brings React where none is needed. |
| Hand-written pages generated by a custom script | Reinvents templating and layout inheritance with less community support. |
| Server-side rendering on the VPS | Public site would depend on the backend, which contradicts ADR 0007. |
